# STAGE 7 — DESIGN CRITIC (style lens): profile-workflows design.md, lines 1–995

- Target: `docs/designs/profile-workflows/design.md`, branch `design/profile-workflows`, lines 1–995 only. Sections 15 and 16 were not reviewed here, except where sections 1–14 refer to them.
- Method: read as a new reader with no prior conversation. Checked against the code the design cites (`core/models.py`, `core/pipeline.py`) and the concepts brief only for term use, not for design approval.
- Rule used for grading: Blocker = a reader or implementer cannot tell what is meant, or two statements in scope contradict each other. Major = a term, message, or repeated rule will mislead a dashboard user or an implementer unless fixed. Nit = wording that adds friction without changing meaning.
- Counts: 7 Blockers, 14 Majors, 12 Nits.
- Note on scope: where this report says an option set "decides" something, that refers only to how the undecided point affects the reviewed lines. The option sets themselves sit in section 16, outside this review range.

## Problems first

### Blockers

**B1 — The working term is not stable, and the document does not survive a rename. Header, lines 6–11; sections 5, 6.2, 7.5, 13.1.**
The header says the concept is called "workflow profile" for now, that section 16 option set A may pick a different name, and that "nothing in the mechanism depends on the word." That last sentence is true only for the mechanism. Everything a user reads depends on the word: the routes in section 13.1 are `/workflows`, the storage directory in section 6.2 is `workflow-profiles`, the error messages in sections 6.1, 6.2 and 7.5 say "flow", the picker in section 13.1 is a "profile picker", and section 5 defines "workflow profile", "flow version" and "flow snapshot" as three separate terms. If option set A picks "flows", the routes, the directory, the messages and the definitions all need changing, and the document gives no single list of the strings that change. A rename is not a find-and-replace of one word; it is a change to at least four vocabularies the document uses at once. Fix: pick one user-facing name for use in all routes, messages, labels and directory names in this document, or list every string that a rename must change.

**B2 — The most-used words are never defined. Section 5, lines 310–343; used throughout lines 1–995.**
Section 5 defines seven terms: workflow profile, flow version, flow snapshot, assurance, goal, suggestion, preset. It does not define "stage", "step", "node", "state", "gate" or "flow" on its own. The document then uses all of them as if they were defined, and uses them for the same thing: section 7.1 calls the items a "stage list" drawn from a "node palette" of "work states"; section 7.2 calls the same items "work steps" with a "gate policy"; section 8.1 calls them "steps" in a "snapshot stage list"; section 13.2 calls them "stages as nodes". The cited code calls them states (`RunState`), not stages, steps or nodes, and the document never gives the mapping from code word to document word. A new reader cannot tell whether step = stage = node, or whether the three words mark three different things. Fix: add one mapping table (code state → document stage → editor node, or drop two of the three words) and define "gate" and "flow" in section 5.

**B3 — Two different rules for which stages cannot be left out. Section 7.3, lines 466–479; section 10.2, lines 697–701; section 7.5, lines 540–544.**
Section 7.3 says five stages may not be omitted: `INTAKE`, `PLANNING`, `VALIDATING`, `EXECUTING`, `INTEGRATING`. Section 10.2 says a profile is refused at save time when it "omits any of `VALIDATING`, `EXECUTING`, or `INTEGRATING`" — three stages, not five. Section 7.5 gives only a `VALIDATING` example for an omitted required stage. Nothing in scope says which statement wins for `INTAKE` and `PLANNING`: are they refused under section 7.3, allowed under section 10.2, or refused somewhere else? An implementer following section 10.2 alone would accept a profile that section 7.3 refuses. Fix: state the non-omittable list once, in one place, and make every other section point to it instead of restating a shorter list.

**B4 — A preset version cannot be both a number and a release. Section 5, lines 336–343; section 6.1, lines 347–353; section 6.3, lines 380–395.**
Section 5 says flow versions are "numbered per profile, starting at 1" and section 6.1 says a profile has a "version number". Section 5 also says presets are "versioned with the Baton release that shipped them" and section 6.3 says "a preset's version is the Baton release that shipped it." A version cannot be both `3` and a release string, and the run record fields in sections 6.4 and 13.1 ("profile id, version") do not say which form a preset run carries. A reader also cannot tell whether a user copy of a preset restarts numbering at 1 or keeps the release version. Fix: define two fields (for example, a preset release tag and a per-profile version number) and say which one the run record stores.

**B5 — The safety label is undecided and its text is programmer shorthand. Section 10.2, lines 692–716; section 10.3, lines 718–733; section 13.1, lines 929–931.**
Section 10.2 says the design's position is "a mix, decided finally by option set B" — so within the reviewed range, the reader does not know whether dropping a safety behaviour refuses the save or only labels the run. That alone leaves sections 7.3, 10.1 and 10.3 unimplementable as written. The label text that is specified does not pass the document's own plain-language test: the stored list is `["quality gate: none", "ship score gate: skipped"]` and the PR body text is "Assurance: reduced — quality gate: none". A dashboard user who is not a programmer cannot act on "quality gate: none" — it does not say what check was skipped, what could now go wrong, or what to do about it. Section 13.1 claims "error text a non-programmer can act on" while section 10.3 specifies text that fails that claim. Fix: write the reduced-assurance label in the same plain form as the section 7.5 loop message (what was dropped, what it means for this run, what the user can do), and state which behaviour classes refuse and which only label, in section 10 itself.

**B6 — An absolute claim the document itself contradicts. Section 7.5, lines 546–550; sections 7.5, 13.2.**
Section 7.5 ends: "A flow that saves cleanly cannot fail differently at run time for a validation reason." The same section says the executor re-checks the snapshot at run start because "a profile edited on disk between save and run start is caught there", and section 13.2 repeats the run-start check. If a clean save could not fail differently at run time, the run-start re-check would have nothing to catch. The claim is also unprovable from the document: section 9.1 itself says a preset can go stale when a model is removed or a check changes meaning, which is exactly a validation reason that appears after save. Fix: replace the absolute sentence with what is actually promised — the editor and the executor run the same validator, so a save-time pass and a run-start pass use the same rules, and a run-start failure names the changed setting.

**B7 — "Snapshot" means two different things. Section 5, lines 320–323; section 6.4, lines 397–408; sections 7.5, 13.2.**
Section 5 defines a flow snapshot as "the profile version frozen onto a run at creation" — a pointer to a version. Section 6.4 defines it as the "full parameter set" resolved and "stored on the run record" — a copy of the parameters. Later uses mix both senses: section 7.5 lists "missing snapshot fields" (a copy has fields; a pointer does not), section 13.2 says a run-start failure "names the snapshot version" (a pointer has a version; a copy does not need one), and section 8.1 says handlers read "from the snapshot" (a copy). A reader cannot tell what is stored on the run record: an id plus a version, or the whole parameter set. That distinction decides storage size, what survives deletion, and what section 14's size cap applies to. Fix: define "snapshot" once as either the stored copy or the version reference, and use a different word for the other sense everywhere.

### Majors

**M1 — Jargon used without definition, across the whole reviewed range.**
A dashboard user who is not a programmer meets these terms with no definition in scope: D1–D6 and "D3 verdict" / "D6 vote" (sections 2.1, 2.2, 3, 8.1 — the letters are never expanded and the decisions are never listed); CDA (section 2.2 — expanded once as "Coding Decision Agent" but its job is described only as "grades a diff", with "diff", "tier" and "threshold 0.7" unexplained); "SimHash fingerprints" and "repo fingerprint" (section 2.5); "handler", "Halt", "resume_state", "lease behaviour" (sections 2.1, 8.1); "allowlist" and "enums" (section 14); "off-loopback token gating" and "checked forms" (sections 2.7, 13.1, stated twice and explained neither time); "shadow mode" and "calibration floors 0.90/0.95/0.98/0.99" (section 2.5 — numbers with no explanation of what a floor does); "workspace profile" (section 9.2 — used as a precedence source but never defined; see M4); "PR body" (section 10.3 — a user who has never opened a pull request cannot place this label). Fix: either define each term at first use in plain words, or move the code-level terms out of user-facing sections and keep them in section 2 only, with a glossary.

**M2 — Several specified error messages fail the document's own plain-language test. Sections 6.1, 6.2, 7.5, 13.2.**
Messages that pass: "Flows do not loop by drawing. Set the round limit on the step instead." (section 7.3) and "EXECUTING cannot run before VALIDATING: execution needs the approved plan." (section 7.5) — each names the problem, the reason, and the fix. Messages that fail: "Gate without a stage is not a flow." (section 7.5 — states a schema fact, gives no fix); "A flow needs at least INTAKE, PLANNING, VALIDATING, EXECUTING, INTEGRATING, in that order." (section 7.5 — five unexplained capitalised codes, no plain names, no fix); "Unknown stage <name>. Stages are INTAKE, PLANNING, VALIDATING, DESIGNING, EXECUTING, INTEGRATING, SHIPPING." (section 7.5 — same code list, and the user never learns what each code means in plain words); "flow <id> version <n> is archived or deleted; pick a current flow" (section 6.1) and "flow <id> version <n> is unreadable" (section 6.2 — placeholders `<id>` and `<n>` are not user text, and "current flow" does not say how to find one). Section 13.2 promises a save failure "lists every error" with "the fix stated", but the catalogue in section 7.5 does not state a fix for every entry. Fix: give every catalogue message the same three parts as the loop message (what is wrong, why, what to do), and replace capitalised codes in user-facing text with the plain stage names the editor shows.

**M3 — The same rule is restated in several places with slight differences, and no statement is marked as the one that wins.**
Examples: snapshot immutability appears in section 4 item 6, section 5, section 6.3, section 6.4 and section 8.3, with different scope each time (edit creates a version; delete archives; resume keeps the snapshot; in-flight runs are unaffected). The unapproved-suggestion rule appears in section 3, section 12.4 and section 12.5. The "never" list appears in section 3 (non-goals), section 12.5 (engine never does) and section 14 (security) — overlapping but not identical lists. The word "never" appears about sixty times in the reviewed range, often as emphasis ("never just stored", "never silently repaired") rather than as a rule. When two restatements differ — as in B3 — the reader has no way to know which one an implementer should follow. Fix: mark one section per rule as normative ("this section states the rule; other sections summarise it") and delete the restatements, or add a line at the top of sections 6, 10 and 12 saying which section wins on conflict.

**M4 — The count of existing "profile" uses does not agree inside the document. Header, lines 6–11; section 2.4, lines 141–151; section 9.2, lines 645–667.**
The header says the term collides with "two existing uses of 'profile' (learning profiles, workspace/server profiles)". Section 2.4 discusses only learning profiles. Section 9.2 then uses "workspace profile settings" as precedence level 3 without ever defining what a workspace profile is, what it contains, or how it differs from a repo `jev.toml` setting at the same level. A reader therefore meets a third "profile" concept — the very collision the header warns about — with no definition and no route or page to attach it to. Fix: define workspace profiles where they first affect the design (section 9.2), or remove them from the precedence table until they are defined.

**M5 — One concept carries three names on the same screen. Sections 6.2, 13.1, 13.2.**
The list page in section 13.1 is `/workflows` showing "profiles" with "scope badges"; the run creation form has a "profile picker"; the run page shows "the snapshot's profile id, version, goal, and assurance badge"; the error messages say "flow". A user on one screen would see "workflow", "profile" and "flow" for the same object, plus "assurance badge" and "assurance note" (section 13.1) for the same label. This is B1 at screen level: the document never fixes the label text for the picker, the list, or the badge. Fix: write out the exact label text for each screen element once, using one name.

**M6 — The document certifies its own honesty instead of showing it. Section 2.6, line 189; section 7, line 426; section 9.1, lines 637–643; section 12.2, lines 833–851.**
"Honest" and "honesty" appear as self-description: "no efficiency claim ... is honest until stage records exist", "the design's central honesty measure", "Two honest statements about this table", "Examples of honest lines". A reader cannot verify "honest" from the document; it is a claim about the author's intent, not a property of the design. The same applies to "make the reduction impossible to miss" (section 10.3) and "first-class path, not an afterthought" (section 13.2) — both assert an outcome the document cannot guarantee. The section 12.2 example reason lines add a second problem: numbers such as "your last 9 graded diffs" and "7 of your last 12 runs" read as measured data but are examples with no source, no window and no completeness flag, while section 11.3 requires every quoted number to carry a sample size and a completeness flag. Fix: delete "honest/honesty" as self-description and replace it with the rule that does the work (for example, "no token number is quoted without a sample size and a completeness flag"); mark every example number as an example.

**M7 — The Efficiency preset row contradicts itself. Section 9.1, lines 609–643.**
The Efficiency stage-list cell reads "Full list minus nothing required". Read plainly, that means the full list minus nothing — the full list. The sentence around it does not say what, if anything, Efficiency leaves out, and the DESIGNING cell says `when_needed`, which is also the default behaviour. The Accuracy column has the related problem in the text below the table: the document admits Accuracy "is close to the default flow plus CDA grading and a production quality level" and asks option set H whether Accuracy "just renames the default" — but the table still presents Accuracy as a distinct preset with no stated difference a user could observe. Fix: rewrite the Efficiency row to list exactly what changes from the default, and either state Accuracy's observable difference or label the column as undecided until option set H.

**M8 — "Gate" carries at least five meanings, and one name does two jobs. Sections 2.1, 2.2, 7.2, 9.2.**
"Gate" means: a waiting state (`AWAITING_*`); a check (quality gate, ship score gate); a decision point (ship gate); a policy on a step (`default` / `require` / `skip` in section 7.2); and a verb ("gate parking", "gate clock", "gate-wait seconds"). Section 2.1 adds a name collision: `AWAITING_APPROVAL` is described as both "the plan gate" and "the EXECUTING gate in `ASK_EVERY_STEP` mode", so one state name covers two different waits. Section 9.2's autonomy exception ("a profile's gate policy `skip` never overrides an explicit human gate the user asked for elsewhere, and a profile never turns an `AUTONOMOUS` run into a gated run or vice versa") is the paragraph a user most needs to understand, and it is the hardest to parse: it never says in plain words when the user will be asked and when they will not. Fix: use one word per meaning (waiting state, check, policy) and rewrite the section 9.2 exception as a short list of cases: user asked for a gate → asked; autonomous → not asked; profile says skip → what happens in each case.

**M9 — The suggestion examples do not follow the document's own number rules. Sections 11.3, 12.2.**
Section 11.3 requires: medians not means; every quoted number carries its sample size; a stage with any `null` attempt is quoted as "at least N tokens" or not quoted; saved tokens from a cache hit are never quoted unless the original cost is known. The section 12.2 examples partly follow this (one line carries "(measured: full)") and partly do not: "your last 9 graded diffs produced no routing change" gives no window and no completeness flag; "3 of your last 10 runs needed a fix task" gives no median, no window, and no statement of whether the 10 runs are in the 90-day freshness window from section 12.3. A reader copying the examples as templates would produce reason lines that break section 11.3. Fix: rewrite the examples so each one carries sample size, window and completeness flag, or label them as shortened illustrations that omit required fields.

**M10 — Four load-bearing decisions are open inside the reviewed range, with no fixed-vs-open list. Sections 6.5, 9.2, 10.2, 13.1.**
Section 6.5 is "proposed; option set E may narrow it" (scope). Section 9.2 is "proposed; option set F may reorder it" (precedence). Section 10.2 is "decided finally by option set B" (enforcement). Section 13.1 is "proposed; final names follow option set A" (routes). The document never collects these in one place, so a reader finishing section 13 does not know which of sections 6, 9, 10 and 13 are settled and which will change. The task brief states none of the eight option sets is pre-picked, so this is expected — but the reviewed sections should say so up front rather than presenting proposed tables as if they were decided. Fix: add a short "decided vs. open" list near the top, naming the four open points that affect sections 1–14.

**M11 — "Default" means at least five things. Sections 5, 7.2, 8.2, 9.1, 9.2.**
"Default" is used for: the `default` preset (section 5); today's pipeline behaviour (section 8.2, "exactly today's code path"); a gate policy value (`default` in section 7.2, meaning "existing behaviour under the run's autonomy mode"); a fallback value in the preset table ("Repo configuration" vs. an explicit default, section 9.1); and precedence level 4, "Baton defaults" (section 9.2). Section 8.2 sharpens the confusion: picking `default` is "a no-op that records the choice and runs the legacy path", so the `default` preset is not a preset that runs — it is a label for not using a profile. A sentence such as "the default flow is unchanged" can therefore mean the preset, the legacy path, or the fallback value, depending on the section. Fix: rename the gate-policy value and the precedence level, and state in section 8.2 that `default` means "no profile" until conformance passes.

**M12 — Assurance is defined from a snapshot that legacy runs do not have. Section 5, lines 324–327; section 8.2, lines 586–599; section 10.3, lines 718–733.**
Section 5 defines assurance as "computed from its snapshot". Section 8.2 says runs without a profile have "no snapshot". Section 10.3 then says assurance is computed "from the snapshot (and, for legacy runs, from the run's effective settings)". The definition in section 5 therefore excludes the legacy case that section 10.3 includes, and section 10.2's claim that the label "applies to every run, profiled or not" rests on a definition that does not cover every run. Fix: define assurance from "the run's effective settings" in section 5, with the snapshot as the source of those settings for profiled runs.

**M13 — "Goal" and "custom" are not pinned down. Section 5, lines 328–333; sections 9.1, 12.1.**
Section 5 says the goal label "changes nothing about execution by itself" and is "the suggestion engine's training signal". Section 9.1 then sets the goal label from the preset (`efficiency`, `accuracy`), so the label is both user-stated (section 12.4: "a suggestion for a stated goal") and preset-assigned, with no rule for which wins when they differ. Section 5 also says a run without a stated goal records `null`, while the goal values are `efficiency`, `accuracy` or `custom` — so `null` is a fourth value that is never listed as a goal, and `custom` is never explained: how does a custom goal differ from no goal, and what does the engine do with a custom goal? Section 12.1 says `null`-goal runs are never used as goal evidence, which leaves `custom` unaccounted for. Fix: list all four values (`efficiency`, `accuracy`, `custom`, `null`) in section 5, say what `custom` means, and state whether a preset's goal label overrides a user-stated goal.

**M14 — "Flow" is used for the object, the drawing, and the run. Throughout lines 1–995.**
"Flow" appears as: the concept itself ("workflow profile", "a run's flow"); the drawing ("a flowchart editor", "the drawing is the stage list rendered as a chain", section 7.1); the execution ("the run executes that profile's flow", section 3); and the stored object ("flow <id> version <n>", section 6.1). Section 4 item 1 ("The drawing lies") relies on the drawing/execution distinction, but the rest of the document blurs it again by calling both the drawing and the execution "the flow". A user who edits "the flow" cannot tell from the wording whether they changed a picture, a stored definition, or a running run — which is exactly the confusion section 6.4 (snapshot) exists to prevent. Fix: reserve "flow" for one sense (the stored definition is the cleanest choice) and use "drawing" for the editor picture and "run" for the execution everywhere else.

### Nits

**N1 — "Stated plainly" and "never silently" are self-praise, not rules. Section 2.2, lines 108–115; sections 6.2, 10.2, 12.5.**
"Existing bypasses, stated plainly because the safety floor must deal with them" praises the document's own tone. "Never silently repaired", "not silently rewritten", "never a silent fallback" repeat "silently" as emphasis; each instance should state the observable behaviour instead (what the user sees, not what the system refrains from doing quietly).

**N2 — Three sentences that need splitting. Section 7.2, lines 452–464; section 9.2, lines 656–667; section 6.5, lines 410–421.**
The `skip` gate-policy definition runs to over sixty words in one sentence with two "never" clauses and a cross-reference. The section 9.2 autonomy exception is one paragraph of four clauses. The section 6.5 scope rule packs both scopes, the cross-scope re-validation rule, and the option-set-E caveat into one paragraph. Each should be a short list of cases.

**N3 — "A tax only new flows pay." Section 10.2, lines 709–711.**
A tax metaphor for a label. A reader cannot tell what is being taxed, who pays it, or what the payment is. Replace with the plain statement: the label applies to legacy runs too.

**N4 — Section 4 headings use metaphor instead of description. Section 4, lines 247–308.**
"The drawing lies", "A second state machine rots", "Presets rot silently", "Suggestions launder thin data", "Precedence fights are invisible". Each heading needs its paragraph to be understood, so a reader scanning headings learns tone, not content. Plain headings would be: "The drawing can differ from the run", "A second interpreter can drift from the pipeline", "Presets can go stale without warning", "Suggestions can overstate thin data", "Precedence can be unclear". The paragraphs themselves are direct; only the headings need changing.

**N5 — Unexplained units and formats in user-facing sections. Sections 6.2, 11.1, 14.**
"JSON" (sections 6.2, 14), "repo" (throughout — never expanded to "repository" at first use), "64 KB per version file" (section 14 — a size cap with no explanation of what a user does when a file exceeds it, or why a profile file would approach 64 KB), "PR body" (section 10.3, see M1). These are small, but they accumulate: a non-programmer meets an unexplained format, unit or abbreviation in nearly every section.

**N6 — "Canonical order" is jargon for "fixed order". Section 7.1, lines 433–450.**
"Canonical" adds nothing a dashboard user needs. The same applies to "subsequence" in the same section ("a profile's stage list is a subsequence of this order") — plain wording is "a profile's stage list keeps this order and may leave some stages out".

**N7 — "Checked forms with off-loopback token gating" is repeated, unexplained, both times. Sections 2.7, 13.1.**
The phrase appears in section 2.7 as an existing pattern and again in section 13.1 as a requirement for new routes. Repetition without explanation in either place means the requirement cannot be checked by a reader. State what the check does in plain words once, and point to it the second time.

**N8 — The editor offers an action that always fails. Section 13.2, lines 938–946.**
Canvas mode lets the user attempt to reorder stages, "in practice: no reordering passes, and the editor says why when one is attempted". An editor control whose only outcome is a refusal message should not be presented as reordering. Say so plainly: the canvas does not offer reordering, and an attempted reorder (for example by dragging) is refused with the section 7.1 reason.

**N9 — "What would falsify it" needs plain wording. Section 12.2, lines 833–838.**
"Falsify" is a technical term. The reason-line form should read: what changes, the evidence, and what would prove it wrong.

**N10 — Inconsistent capitalisation of defined terms. Sections 5, 6.4, 13.1.**
"Flow version" and "Flow snapshot" are capitalised in section 5 but appear as "flow snapshot", "flow version" and "snapshot version" elsewhere; "Assurance" is capitalised in section 5 and lower-case in most later uses. Pick one form per term and use it everywhere, so a reader can tell a defined term from an ordinary word.

**N11 — "A profile never invents a model, a provider, or a price." Section 7.4, lines 501–504.**
Models and providers are introduced in the surrounding lines; "a price" is not. Nothing in section 7.4 says profiles carry prices, so the third item reads as a rule about something that does not exist in the design. Delete "or a price" or say where a price could appear.

**N12 — "Gate-wait" vs. "gate waiting" vs. "gate-wait seconds". Sections 11.1, 11.2.**
Three forms for one quantity ("gate_wait_seconds", "gate waiting is recorded separately", "gate-wait seconds"). Use one plain form in prose ("time spent waiting for approval") and keep the field name only in the schema list.

## What reads as specified rather than asserted

This section is short by design: the findings above come first, and this part records only the places where the reviewed lines state a rule together with its consequence, so the fix list does not have to re-litigate them.

- The loop message in section 7.3 ("Flows do not loop by drawing. Set the round limit on the step instead.") gives the problem, the reason and the fix in one sentence. The catalogue in section 7.5 should match this form (see M2).
- The `null`-means-unknown rule in section 11.1 ("`null` means unknown, never zero") and the "at least N tokens" rule in section 11.3 give a reader a testable statement about numbers. The section 12.2 examples should meet the same test (see M9).
- Section 4 names each failure mode and the section that answers it. That structure is what makes the repetition findings above checkable: each restatement can be compared against the section 4 entry.
- Section 12.4 states the approval boundary in four steps (ask, draft stored as a suggestion record, approve or discard, approval covers one version only). The boundary is stated; the wording problems are in the terms it uses (see B2, M13), not in the shape of the rule.

## Fix order, if only some items are fixed before implementation

1. B2 (define stage/step/node/gate/flow) and B1 (one user-facing name) — without these, no other wording fix sticks, because later fixes will use the same shifting words.
2. B3, B4, B7 (one non-omittable list; one version scheme; one meaning of snapshot) — these are contradictions an implementer cannot resolve by choosing the clearer sentence.
3. B5 and M2 (plain safety label; plain error catalogue) — these are the only words a dashboard user will actually see, and they currently fail the document's own plain-language test.
4. B6, M3, M6 (remove absolute and self-certifying claims; mark one normative statement per rule) — these remove the sentences a skeptic cannot verify.
5. The remaining Majors and Nits, in section order, during the re-audit the header already promises if option set A renames the concept.
