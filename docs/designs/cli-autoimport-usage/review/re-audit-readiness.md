# Re-audit — Implementation Readiness (§9–§10)

* **Design reviewed:** `docs/designs/cli-autoimport-usage/design.md`, lines 1057–1371 (§9.0 probe gate, §9.1 Phase A, §9.2 Phase B, §9.3, §10 verification)
* **Against:** `review/consolidated_review_report.md` (C1–C30, X1–X4)
* **Verdict: NOT READY.** Five blockers. The plan is much closer than the draft — the file lists are correct, the paths check out, most values are present — but the fetcher has no defined interface, the precedence function and the shared credential reader are still unnamed, the probe gate has no failure branch, the opt-in write path is missing, and the refresh button's mechanism is undefined. An implementer would have to invent all five mid-build.

## Blockers

### B1 — The `UsageFetcher` has no interface: no constructor, no method names, no config source (C3, C14, C16)
* **Section:** §9.1, `fetcher.py` bullet (~lines 1134–1140); `core.py` bullet (~lines 1167–1172); `routes_connections.py` bullet (~lines 1183–1190).
* **Gap:** §9.1 says "construct `self.usage_fetcher` in `DashboardCore.__init__`" and "the connections page render may start a background fetch through the fetcher" — but it never names a single method on the fetcher, never gives its constructor arguments, and never says how it learns the things it must enforce. The fetcher has to know the `[usage]` kill switch (repo config), the home directory, the adapters, and the cache. `DashboardCore.__init__` takes `settings`, launchers, and runners — it takes no `JevConfig`, and repo config is loaded per request through `open_repo` inside each route handler. So a process-wide fetcher built once at startup cannot see the kill switch unless the config is passed in on every fetch call, or the fetcher reads config itself — §9 picks neither. Likewise the trigger check (enabled + floor + kill switch + login present) has to be evaluated somewhere, and the method that evaluates it is unnamed: is it `refresh(provider)`, `maybe_fetch(provider)`, `request_fetch(provider, config)`? The test list asserts "second `refresh()` returns False while one runs", so a method called `refresh` exists in the tests' mind, but its signature, its arguments, and who calls it from the page render are all unstated. The lifecycle location (C16) is closed; the interface is not. An implementer must design the fetcher's whole public API.

### B2 — The precedence resolution function is still unnamed, with no signature or return type (C8)
* **Section:** §9.1, `provider_auth.py` bullet (~lines 1150–1157).
* **Gap:** §9.1 says "the precedence resolution function (one function, §6.2 tables as its test list — one case per row: 5 Claude, 4 Codex)". It gives no name, no parameters, and no return type. C8 required the design to name the function and its return type in §6.1/§9. §6.1 (~lines 556–560) is no better: it calls it "one resolution function in `provider_auth.py`" with no name either. The function is the single decision point for which credential workers use, which credentials are present, and which credential usage is measured against — the implementer cannot write it from this text without inventing its shape. The same bullet names `get_login_source(provider) -> LoginSource` but gives it only one parameter, while the existing `claude_code_auth`/`codex_auth` take `home`, `env`, and `which` for injection; §9 never says how tests inject a fake home or fake environment into `get_login_source`, or whether it reads `Path.home()` and `os.environ` directly. Not closed.

### B3 — The probe gate has no failure branch and no pass conditions for items 3–7 (C1)
* **Section:** §9.0, lines 1059–1088.
* **Gap:** Only items 1 and 2 carry a pass condition. Item 3 (Claude success rate) says "repeat the call over a short observation window (one hour of normal Claude Code use)" with no attempt count and no decision rule: what measured rate maps to what cadence? The item claims "this sets the cadence check for D6" but gives no rule for turning the measurement into a number, so the probe cannot settle D6 as C1 requires. Items 4–7 are record-only ("record accepted or rejected", "record whether…") with no pass/fail attached. There is no script path or language for the "throwaway script", no redaction procedure for the raw responses (which fields are token values, how they are stripped), and no stated contents for `PROBE.md` beyond "summary". Worst, there is no failure branch: the gate says "implementation does not start until the probe records exist", but records of a failed probe also exist. If the Claude endpoint returns 404, or the Codex success shape differs from the design's parser, does Phase B get dropped, does the design go back for another resolve, or does implementation proceed anyway? Nothing says. A gate with no defined outcome for failure is not a gate. Item 2's pass condition ("at least one window carrying `utilization` and `resets_at`") also does not require recording the `limits[]` field names and types, even though the §9.2 parser depends on "structure per the probe record" — the one fact the parser needs most is the one the checklist does not explicitly demand.

### B4 — The opt-in write path is missing: nothing persists `enabled: true` (C4)
* **Section:** §9.1, `routes_connections.py` bullet (~lines 1183–1190), `templates/connections.html` bullet (~lines 1191–1197), fetcher test list (~line 1242).
* **Gap:** C4 makes "Check usage" a per-provider opt-in that persists in the cache record (`enabled: true`), and the fetcher test asserts "no fetch before opt-in (`enabled` false → zero calls)". But no step in §9 performs the transition from `enabled: false` to `enabled: true`. The refresh-route bullet describes the route's responses (redirect + flash, rate-limited flash, 404, kill-switch flash) and never mentions writing `enabled`. The template bullet names a button with a `data-usage-refresh` attribute but no form action, no route, and no statement that clicking it persists anything. The cache bullet lists `enabled` as a stored field but never says which code writes it. An implementer must invent the write path — and a wrong guess (for example, the refresh route setting `enabled` on every click vs. a separate enable step) changes the consent behaviour the design is careful about elsewhere.

### B5 — The refresh button's mechanism is undefined, and the `conn.js`/template contract is only a selector (C14, C30)
* **Section:** §9.1, `templates/connections.html` bullet (~lines 1191–1197), `conn.js` bullet (~lines 1188–1190).
* **Gap:** The template bullet gives the button a `data-usage-refresh` attribute. The `conn.js` bullet only covers poll updates ("updates the `[data-provider-usage]` block in place… never triggers a fetch") and says nothing about the button. Nothing in §9 states whether the button is a `<form method="post">` to the refresh route (the existing pattern everywhere in `connections.html`, with `csrf_input()`) or a JavaScript POST issued by `conn.js`. If it is a form, `conn.js` needs no button code and the attribute is unexplained; if it is JavaScript, the POST, the CSRF handling, and the response handling are entirely undesigned. Separately, the `[data-provider-usage]` block's inner structure is undefined: which sub-elements `conn.js` must update for each state (bar widths, "updated … ago" text, button label switching between "Check usage" / "Refresh usage" / "Checking…", disabling Refresh until the next-retry time) is left to the implementer, even though the template and the script are two files sharing one DOM contract. The poll JSON shape is specified; the DOM it is rendered into is not.

## Majors

### M1 — The "one shared reader" for credential values is unnamed and does not exist yet (C14)
* **Section:** §9.1, `provider_auth.py` bullet (~lines 1150–1157); §6.1 (~lines 556–575).
* **Gap:** §9 says "the shared credential-file reader used by both detection (presence) and the adapter (values)". No such single function exists in the repo: presence is checked by two separate readers (`_credentials_login` for `~/.claude/.credentials.json` and `_codex_auth_file` for `~/.codex/auth.json`, `provider_auth.py:106–130`). §9 never names the new function, its parameters, or its return type, and never says which of the two existing readers is generalised. C14 required the adapter to read values "through one shared reader in `provider_auth.py` (the existing credential-file reader, generalised)" — the design repeats the requirement without supplying the name or shape. The implementer designs a security-sensitive reader from scratch.

### M2 — Codex adapter: package-version source and `PopenFn` type are undefined (C21)
* **Section:** §9.1, `codex.py` bullet (~lines 1105–1119).
* **Gap:** The `initialize` params carry `"version": "<package version>"` but §9 never says where that string comes from. `jev_agent.__version__` exists (via `importlib.metadata`); the design does not name it, so the implementer guesses. The spawner is "injected (named `PopenFn`, matching the existing `popen` injection in the flows)" — but `PopenFn` does not exist anywhere in the repo, and the existing injection is a bare `popen: Callable[..., Any] = subprocess.Popen`. No callable signature is given for `PopenFn`, so the name is new and its type is undefined. Two smaller gaps in the same bullet: the 4 MiB output cap has no enforcement mechanism (incremental read with a running count? kill when exceeded? checked after the process ends?), and an `initialize` acknowledgement carrying an error result has no handling — only "no ack" is covered by the tests.

### M3 — `Retry-After` has nowhere to live (C6)
* **Section:** §9.1, `cache.py` bullet (~lines 1121–1133) and `fetcher.py` bullet (~lines 1134–1140); §9.2 test list (~lines 1286–1289).
* **Gap:** The fetcher "honours `Retry-After`", and the Phase B test asserts "next attempt no earlier than `Retry-After` seconds". But the cache record's field list (`schema_version`, `enabled`, `fetched_at`, `last_attempt_at`, `last_status`, `last_reason`, `source_version`, `account_hash`, `windows`) contains no next-retry field, and §9 never says where the wait is stored (in-process fetcher state? unnamed field?) or whether it survives a dashboard restart — if it does not survive, a restart immediately retries into a rate limit, and the design never says whether that is acceptable. The test therefore has no observable seam: a test cannot check "no earlier than `Retry-After`" without knowing where the deadline is kept. The companion assertion, "429 does not count toward any failure tally", is untestable as written because no failure tally exists anywhere in the design — it asserts the absence of a thing that was deleted.

### M4 — The expired-token signal is undefined (C2)
* **Section:** §9.2, test list (~lines 1295–1297).
* **Gap:** "Expired token → reason `token_expired_refresh_failed`; nothing is written to `~/.claude/.credentials.json`." §9.2 never says what tells the adapter the token is expired: is `expiresAt` checked before the call (a pre-check that avoids a wasted request), or is expiry inferred from a 401 response (which first looks identical to `unauthorized`)? The two readings produce different behaviour — a pre-check never burns an attempt, a 401-only reading spends one attempt and needs a rule for telling "expired" apart from "rejected". C2's decision ("an expired token is `token_expired_refresh_failed`") is stated; the signal that produces it is not. The implementer decides.

### M5 — The 401/403 re-arm is untested and its mechanism is unnamed (C7)
* **Section:** §9.2, test list (~lines 1289–1291); §9.1 `fetcher.py` bullet (~lines 1134–1140).
* **Gap:** The Phase B tests cover the stop ("exactly one retry, then no further attempts until auth state changes or manual Refresh") but no test covers the re-arm itself: a detection change resuming fetches, or a dashboard restart clearing the stop. And the mechanism is unnamed: the stop lives "in process memory only" and is re-armed by "detection change", but §9 never says what stores the stopped state, what is compared on each view (the `LoginSource` kind? the source path? both, per D7), or which component performs the comparison — the fetcher, the route, or the adapter. The stop is specified; the way back out of it is not.

### M6 — Test gaps against §9's own rules (C18, C29, C30)
* **Section:** §9.1 test list (~lines 1210–1256); §9.2 test list (~lines 1281–1304).
* **Gap:** Four cases the design's own rules require have no test, and one test has no pass condition:
  * Duplicate `windowDurationMins` → `unexpected_response` is in the `codex.py` bullet (line 1116) but has no test case; only unknown duration and `primary` null are tested.
  * `resets_at` in the past → renders "resetting…" is tested for Codex only; the same rule (C18) applies to Claude and has no Claude test.
  * No `endpoint_changed` test (404/410 from the usage endpoint) exists in Phase B, although §6.5 defines the code and C29/C30 require it.
  * No Claude single-window test: C18 says when only one window is present the adapter shows the one present rather than failing, but §9.2 tests only the happy path and the both-missing case.
  * The Claude happy path says "two windows + splits ignored-or-included per the probe record" — "ignored-or-included" is not a pass condition. A test cannot be written from this line; §9 never says the probe record's field mapping becomes the test fixture.

### M7 — `left_percent` has no conversion point; Claude's `plan` value is undefined (C14)
* **Section:** §9.1, `__init__.py` bullet (~line 1100) and `routes_connections.py` bullet (~lines 1178–1182).
* **Gap:** The model carries `used_percent`; the live-poll JSON and the rendered bars carry `left_percent`. Nowhere in §9 — and, checked by search, nowhere in the whole design (there is no `100 −` anywhere in the file) — is the conversion assigned to the adapter, the cache serialisation, the view, or the template. Three files touch the number and each could reasonably own the subtraction. Separately, the poll JSON includes `plan` for both providers, but only Codex has a `planType`; §9 never says what the Claude snapshot carries for `plan` (`None`? omitted? a fixed string?). Small, but the wire contract is the thing C14 was supposed to pin down.

### M8 — Config registration is missing its label; fetcher shutdown bound vs. lifespan timeout is unresolved (C15, C16)
* **Section:** §9.1, `settings.py` bullet (~lines 1163–1165); `fetcher.py` bullet (~lines 1134–1140).
* **Gap:** `TOP_SECTIONS` entries are `(path, label)` tuples, and the label is user-visible on the Settings page. §9 says "register `[usage]` in `TOP_SECTIONS`" without giving the label string, so the implementer invents visible copy. (Page placement itself is fine — verified: unclaimed sections land on Settings automatically.) Second, the fetcher "joins threads with a 5-second bound", but `shutdown_jobs` receives `JOB_SHUTDOWN_TIMEOUT_S = 30.0` from the lifespan — §9 never says whether `shutdown()` takes that timeout as a parameter or hardcodes 5 seconds, nor where the 5 seconds sits relative to the 30. A five-line clarification, but it is a real ambiguity in the shutdown path.

### M9 — The fake-clock seam is named as a phrase, not a seam (C30)
* **Section:** §9.1, test files (~lines 1141–1143).
* **Gap:** C30 explicitly required the fake-clock seam to be named. §9.1 says the cache and fetcher tests use "a fake clock" but never says what the seam is: an injectable clock argument on the cache/fetcher constructors? a monkeypatched module-level time function? which module's `time`? The home seam is named ("home directory supplied as a parameter", line 1132) — though not to which constructor — while the clock seam is only a phrase. The tests cannot be written without inventing it.

### M10 — The manual-refresh-inside-floor test contradicts the route's own behaviour (C5)
* **Section:** §9.1, test list (~lines 1236–1240); `routes_connections.py` bullet (~lines 1183–1190).
* **Gap:** The fetcher test says a manual refresh inside the floor is "ignored…, returning the cached value". But the refresh route returns a redirect + flash through `act()` — it does not return a cached value to anyone. The observable the test should assert is unclear (redirect + flash naming the wait? a JSON body?). The same vagueness affects the rate-limited flash: "redirect + flash naming the wait" gives no exact string and never says where the wait comes from (the floor remainder? `Retry-After`? whichever is later?). The floor rule itself (C5) is correctly stated; its observable is not.

## What is ready

The file lists are complete and correct against the repo, the config paths are right, the Codex wire values are carried into §9.1, the per-phase gates in §10 are concrete (including the `secondary`-null branch and the "unit-proven only" note for 429), and the test list is mostly reason-coded with observable passes. The remaining work is concentrated: define the fetcher's interface and config source, name the precedence function and the shared reader (with signatures), give the probe a failure branch and decision rules, state where `enabled` gets written, and pin down the refresh button's mechanism.
