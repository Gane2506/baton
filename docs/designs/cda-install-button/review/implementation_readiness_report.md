# Implementation Readiness Test — Stage 9 Goldfish review

- **Target:** `docs/designs/cda-install-button/design.md`, section 8 (lines 765–855) and section 10 (lines 1131–1191).
- **Context used, and only that:** sections 1–7, 9, 11, 12 for dependencies; `concepts_brief.md`; and the listed code files (`code_grade.html`, `backend.py`, `laya_backend.py`, `browser_install.py`, `code_grade_runner.py`, `core.py`, `routes_code.py`, `security.py`, `learning.html`, `pyproject.toml`, `docs/code-orchestrator.md`, `docs/deploy.md`, `Dockerfile`).
- **Standard applied:** `implementation-readiness-standard.md` — a competent engineer unfamiliar with the codebase must be able to execute the plan on the first attempt without guessing, asking clarifying questions, or making independent design choices (the zero-decision rule), in phases that each leave the codebase stable, buildable, and testable.
- **Verdict: FAIL.** Section 8 is a file list with conditional branches, not a decided, phased, executable plan. Section 10's criteria are largely conditional or procedural shells without the thresholds, procedures, and oracles that would make them measurable. Picking one option per set in section 9 would **not** by itself fix this: Blockers B3–B9 below survive every section 9 choice, because the missing decisions are delegated to the implementer (or to testing) rather than to the human gate.

## Blockers

### B1. Section 8 has no phases, ordering, or checkpoints — §8, lines 765–855
**What is wrong:** The standard requires work partitioned into logical, incremental phases, each leaving the codebase stable, buildable, and testable. Section 8 is a single flat bullet list of 16 file entries with no sequence (runner before routes? templates before routes? docs last?), no per-phase build/test gate, and no rollback step if a phase fails. An implementer cannot tell what a first shippable slice is, or what must stay green between slices.
**Evidence:** Section 8, lines 765–855, is one unnumbered list; no phase headings, ordering words, or checkpoints appear in it. The only sequencing statement is the final bullet (line 846) saying the design itself is updated before implementation starts.

### B2. Section 8 is itself conditional on undecided option sets, and admits it — §8, lines 771–855; §9
**What is wrong:** The plan cannot be executed as written because its own file list changes with the human's picks, and several picks create work that section 8 never lists. Examples: the runner filename is "new, **or** the shared-scaffold file from option set B" (line 771); the confirm route exists only "if option set H picks one" and the stop route only "if option set E picks one" (line 784); the D2/D3 config-write path has no file, route, or test entry at all; the G2 uninstall action has no route or test entry (see M11). Section 8's last bullet concedes the point: the design must be "updated with the human's option-set decisions before implementation starts, so the implementer works from a decided spec, not from open options" (line 846). That is a correct admission that the current section 8 is not that decided spec.
**Evidence:** §8 lines 771, 784, 815, 846; §9 sets A–H are all explicitly unpicked ("None is ranked, none is marked as preferred, and none is pre-picked").

### B3. GPU/torch-path detection is explicitly delegated to the implementer — §8 line 771 (via §5.3, line 347); §10 line 831
**What is wrong:** The fixed argv, the honest sizes, preflight disk math, and the platform matrix all depend on the CPU-vs-default torch decision, but the design says: "The exact detection call is an implementation detail the implementer must name in code review, because a wrong detection on a CPU-only host is the 2.5 GB mistake this section exists to prevent." That is the zero-decision rule violated in its own words: the single most expensive decision in the feature is left to the implementer, with the failure mode named but the detection call, its inputs, its fallback when detection is inconclusive, and its test double all unnamed. Section 8's matrix-test bullet ("environment detection stubbed per cell", line 831) stubs a function that section 8 never names or specifies.
**Evidence:** Design line 347; §8 line 771 (argv building) and line 831 depend on it; `docs/code-orchestrator.md` documents the CPU-first sequence manually but names no programmatic detection.

### B4. Branch-2 dedicated venv: path unspecified, and the grade-runner change it requires is missing from section 8 — §8 lines 779, 800 (via §5.4, line 386)
**What is wrong:** Section 5.4 says the dedicated-venv location is "a fixed path under the dashboard's state directory (for example `<state>/.jev/cda-venv` — the exact path is an implementation detail, but it must be one fixed path, recorded in the durable job record, and the dashboard must discover it on the next start by checking that path, not by searching)." A path that is simultaneously "must be one fixed path" and "an implementation detail" is not a specification: the implementer must invent it, and every later reader (job record, discovery, docs, tests) must agree with that invention. Worse, section 5.4 adds that "the grade runner must accept an interpreter override; if it cannot, this branch is unavailable" — but section 8's `code_grade_runner.py` bullet (line 800) lists only the `unavailable_message()` change and the ledger guard. There is no bullet modifying the grade runner (or `backend.py`'s loader, or the `_orchestrator` seam in `routes_code.py`) to accept, store, or use an interpreter override, and no bullet for the next-start discovery check. Branch 2 therefore has no implementable wiring in the plan.
**Evidence:** Design line 386 (`<state>` is itself a placeholder, not a defined directory — see B5); §8 line 800 omits any interpreter-override work; `code_grade_runner.py`'s `_orchestrator` builds `CodeOrchestrator(model_id=..., max_diff_chars=...)` with no interpreter parameter, and `backend.py`'s `load_backend` uses the running interpreter's `find_spec`.

### B5. The durable job record has no location, schema, or identity — §8 line 771 (via §6.5, line 559)
**What is wrong:** Section 6.5 requires a durable record in "a fixed location (the dashboard state directory, not a repo's `.jev/` directory)" recording "the fixed argv sequence, the target environment decision, the started time, the current phase, the exit code when finished, and the verification outcome." None of these is specified to an implementable level:
- **Location undefined.** The listed code has no global "dashboard state directory": `DashboardSettings` carries a repo `root`, and `BrowserInstallRunner(root)` writes `root/.jev/browser-install.log`; the only global state path in the listed files is `~/.jev/dashboard-secret` in `security.py`. Section 5.4's `<state>` placeholder does not resolve this. The implementer must invent the directory, its creation, its permissions, and its behaviour when it is unwritable.
- **Schema incomplete for its own purpose.** The listed fields contain no process id, no log path, no model id, no torch-path decision, and no failure class — yet section 6.5's restart rule requires deciding whether "no living child process" exists, which is uncheckable without a stored pid (or an equivalent liveness mechanism, also unnamed). There is no format (JSON? SQLite? file per job?), no atomic-write rule, no locking rule for two dashboard processes, and no retention rule.
- **Consequence.** The `interrupted` state, the restart acceptance criterion (§10), and the cross-repo banner (§6.9) all rest on this record. Without its schema and location, none of them can be built from the plan alone.
**Evidence:** Design line 559 and §8 line 771 (runner bullet names "durable job record" but gives no file, format, or fields); `browser_install.py` (repo-scoped log) and `core.py` (`settings.root`) show the only existing patterns, both repo-scoped, contradicting the "not a repo's `.jev/`" requirement without supplying the alternative.

### B6. The verification probe has no executable contract — §8 lines 771, 810 (via §5.2, line 305)
**What is wrong:** Section 5.2 requires a fresh-subprocess probe, but the plan never gives the implementer the probe itself:
- The probe command as written is not executable verbatim: "`sys.executable -m python -c ...`" (line 305) — `sys.executable` already names the interpreter, so `-m python` is a malformed invocation. No corrected command, no `-c` script body, no expected stdout/exit-code contract, and no timeout are given.
- The loadability step is conditional in a way that forces implementer research: "constructs the backend object without loading the checkpoint, **if the backend API allows it**; otherwise the probe stops at the import step and says so plainly." The listed code actually answers this — `LayaBackend.__init__` stores the model id without importing `laya` or loading anything, while `_agent_or_load` is the step that calls `laya.load(model_id)` — but section 8 does not name that entry point, does not say whether the probe constructs `LayaBackend` directly or gains a new entry point, and hedges `backend.py` as "modify only if needed" (line 810). The implementer must decide the probe's construction path.
- The checkpoint probe (step 3) names no cache-traversal rule: given a model id and `$HF_HOME` or `~/.cache/huggingface/hub`, which directory/file proves "present and readable" is unspecified (snapshot layout, filename, partial-download markers all unnamed).
- The A2 warm-up phase has no mechanism at all: no function exists in the listed code that downloads a checkpoint without grading (the only fetch path is a real grade through `laya.load`), and section 8 lists no new warm-up function, module, or `laya_backend.py` change to create one. A warm-up that simply calls `laya.load` in a subprocess would load torch plus the model (2–3 GB) and is never specified as such, with no memory, timeout, or exit criteria.
**Evidence:** Design line 305; §8 lines 771, 810; `laya_backend.py` lines 459–481 (`__init__` lazy, `_agent_or_load` loads); `backend.py` `load_backend` returns `LayaBackend(model_id)` without loading, so `CodeOrchestrator.available` (which calls `_backend()`) is a presence-level check, not the loadability probe section 5.2 requires — the gap the probe must fill is real, but its contract is missing.

### B7. The fixed argv is a rule, not a sequence — §8 lines 771, 820 (via §7.1)
**What is wrong:** Section 7.1 correctly states the security rule (constant server-side argv, never from request data, `jev-agent` never in it), but section 8 never gives the argv itself, and several of its components are undecided or technically unresolved:
- **Torch specifier:** no version, no pin policy, no flags. Section 5.3 says the CPU path installs torch "without letting pip re-resolve torch to the default wheel" — but names no mechanism. Plain `pip install laya` after a CPU torch install re-resolves torch unless dependency resolution is constrained (e.g. `--no-deps`, which would also drop `laya`'s other dependencies such as transformers, or a constraints file, which is never mentioned). The implementer must solve the pip resolver puzzle.
- **`laya` specifier:** deferred to option set G, and G1/G2 say to keep `laya>=0.4.15` "unless the implementer finds a breaking version during testing, in which case the policy becomes a pin and the design is amended" — a version decision delegated to implementer testing, not to the human gate. The argv therefore cannot be written until testing, and `pyproject.toml` (the only place `laya>=0.4.15` is declared) has no section 8 entry at all, so a pin would have no planned file change.
- **Branch-2 argv:** whether the venv's pip needs bootstrapping (`ensurepip`), and which interpreter path the argv uses, is unspecified (see B4).
- **CPU index literal:** section 7.1 says the PyTorch CPU index is "a constant in code" but never quotes it; the literal exists only in `docs/code-orchestrator.md` (`https://download.pytorch.org/whl/cpu`). A plan that requires a constant should state it.
**Evidence:** §8 lines 771, 820 (argv tests assert a property of an argv the plan never writes); `pyproject.toml` line 46–47 (`laya>=0.4.15`); §9 G1/G2 wording delegating the pin to testing.

### B8. The Docker persistence answer that section 8 and section 10 depend on does not exist in option set G — §8 line 839; §10 line 1190 (via §5.4, line 423)
**What is wrong:** Section 5.4's Docker row says "See option set G" and "The ephemerality warning, or the volume path, per option set G." Section 8's `docs/deploy.md` bullet requires "the Docker persistence answer from option set G," and section 10's rollback says "add the volume from option set G and reinstall once." But option set G (G1 first-install-only, G2 minimal lifecycle, G3 version policy) contains no volume name, no volume mount path, and no statement of which paths a volume would need to cover. This is not a minor omission: the listed `Dockerfile` runs as non-root user `jev` with workdir `/data` and no volume for site-packages, and section 2 notes only an "optional named volume `jev-state` for state." A state volume does not by itself persist a container-side pip install into system site-packages unless the install target itself is relocated onto the volume — a relocation the design never specifies. So even after the human picks a G option, the implementer has no Docker answer to implement or document, and section 5.4's normative rule ("The button must never be shown on Docker without that statement") cannot be satisfied from the plan.
**Evidence:** §5.4 Docker row (line 423); §8 line 839; §10 line 1190; `Dockerfile` (no site-packages volume; `USER jev`, `WORKDIR /data`); §9 G1–G3 text (no volume specification).

### B9. The install/grade coordination lock has no API, and the grade-refusal path has no planned code change — §8 lines 779, 800 (via §6.4)
**What is wrong:** Section 6.4 requires a coordination point "owned by `DashboardCore` (or its equivalent), not inside either runner," with blocked states in both directions and a ledger guard for refused grades. Section 8 names this only as "own the install/grade coordination lock" in the `core.py` bullet (line 779). It specifies no lock type, no method names, no acquisition order, no exception type for a refused grade, and no UI surface for the "waiting" state. Concretely, the listed `routes_code.py` grade/route handlers catch only `CodeGradeBusy`; there is no planned exception or return path for "refused because an install is running," and the `code_grade_runner.py` bullet (line 800) mentions the ledger guard but not a new refusal API on `CodeGradeRunner.start` or a coordination check in the handlers. The implementer must design the lock interface, the refusal signalling, and the waiting UI — the core of section 6.4.
**Evidence:** §8 lines 779, 800; `routes_code.py` handlers catch `CodeGradeBusy` only; `code_grade_runner.py` `start` raises `CodeGradeBusy` on a live thread and `_work` ledgers `unavailable` for failed jobs — the "refused grade ledgers nothing" path (§6.4) requires a refusal that never reaches `_work`, which no bullet designs.

### B10. Section 10's acceptance criteria are conditional, disjunctive, or lack a procedure — §10, lines 1133–1151
**What is wrong:** A criterion that passes under whichever option the human later picks, or that has no defined setup/teardown, is not measurable as written:
- "the status panel reports installed **per option set A**" — A1, A2, and A3 produce different panel states (flip on probe, flip on warm-up, two-line state). The criterion is three different assertions wearing one sentence; no per-option oracle is given.
- "grading can be enabled from the UI **per option set D (or the panel states the Settings path, per D1)**" — a disjunction that passes under either D1 or D3 without saying how enablement is verified (panel text? config file value? a subsequent gate grade?).
- "one click (plus a confirm click **if option set H picks one**)" — the click count, the test's steps, and the pass condition all change with H.
- **Live-test setup undefined.** "From a fresh 'not installed' state on the Mac live dashboard" has no procedure for reaching that state (uninstall `laya`? torch? clear the Hugging Face cache? reset which venv?) and no teardown. Under G1 there is no uninstall action at all, so the tester cannot even re-create the fresh state from the browser; the setup would itself require the terminal use the criterion claims to avoid.
- **No oracles for the negative criteria.** "No install outcome is written to the grade ledger" names no ledger file to inspect, no query, and no before/after comparison (the ledger path is per-repo in the listed code, while the install is machine-wide — which repo's ledger is checked is unspecified).
**Evidence:** §10 lines 1133–1151; §9 sets A, D, H; `code_grade_runner.py` `_record`/`ledger_path_for_repo` pattern (per-repo ledger) vs §6.9 machine-wide install.

## Majors

### M1. Preflight has no numbers, methods, or refusal thresholds — §8 lines 771, 820, 831; §10 lines 1153–1167 (via §6.1)
**What is wrong:** Section 6.1 requires disk (target disk and temp disk, covering torch variant + checkpoint + temp staging), memory ("at least the 2–3 GB … or a warning"), writability, and network reachability checks, each mapping to a plain-English refusal. Section 8 provides no byte thresholds, no formula (is checkpoint counted when A1 is picked? is temp staging 1 GB on top of, or inside, the total?), no memory threshold that distinguishes refusal from warning, no reachability method (socket connect? HTTP HEAD? pip dry-run?), no host list, and no timeout. The test bullet ("preflight refusal tests") therefore has no values to assert, and the matrix bullet ("Tests stub … disk, and network") stubs detectors that do not exist in the listed code — neither runner has a disk or network seam; `BrowserInstallRunner`'s only seam is process spawn. The implementer must invent every threshold and seam.
**Evidence:** §6.1 text (qualitative requirements only); §8 lines 820, 831; `browser_install.py` (`spawn` is the only injected seam) and `code_grade_runner.py` (executor seam only).

### M2. Failure classification has no signals — §8 line 820 (via §6.2)
**What is wrong:** Section 6.2 says the runner "classifies by exit code, pip output markers, and probe output" and tables 11 conditions with messages and retry offers. It lists no pip exit codes, no output markers/regexes, and no probe-output patterns that distinguish the conditions that matter in practice — disk-full during download vs temp-directory-full vs permission-denied vs PEP 668 refusal vs hash mismatch all surface through pip stderr in overlapping wording. The classification-test bullet (line 820) therefore has no fixtures to test against. An implementer must reverse-engineer pip's output taxonomy and hope it matches the test author's.
**Evidence:** §6.2 table (messages and retry columns only, no signal column); §8 line 820.

### M3. The route table is incomplete: one path for a "pair," no methods, no GET/POST/CSRF split — §8 line 784; §10 line 828
**What is wrong:** Section 8 says "the install route pair (`/code-grade/install`, status plus live fragment)" — one path for two endpoints. The existing pattern it claims to mirror is two distinct routes (`/code-grade/status` and `/code-grade/live` in `app.py`), so the install pair presumably needs `/code-grade/install` and something like `/code-grade/install/live`, but the second path is never stated. No methods are given for install, confirm, stop, or repair (the existing grade/cancel pattern mixes GET-tolerant POSTs and POST-only actions, and `checked_form` applies to POSTs — see `security.py`), and no statement says which of the new endpoints are GET (status/live) vs POST (start/stop/repair) or which carry CSRF. The routes-test bullet (line 828) lists "CSRF refusal" without saying which route's CSRF refusal is tested.
**Evidence:** §8 line 784; `app.py` route list pattern (`/code-grade/status`, `/code-grade/live`, `/code-grade/cancel` POST-only); `security.py` `checked_form` (POST form + CSRF).

### M4. The template changes have no context contract — §8 lines 791, 795 (via §6.7, §6.8)
**What is wrong:** Section 8 says `code_grade.html` gains "the Install button, the install banner, the Backend row's install states" and a new status template plus live fragment, but never says what context the routes pass to those templates. The listed `routes_code.py` `code_grade_page` build returns only `settings`, `available`, `job` (the grade job), `form`, and error fields — there is no install-job status, no banner data, no Backend-row install state, and no per-cell persistence statement in the context. The implementer must invent context keys, and the new status template's context (phase, elapsed time, log tail, full-log link) and polling mechanism are likewise unnamed (see N1). A template bullet without its context is not implementable without design work.
**Evidence:** §8 lines 791, 795; `routes_code.py` `code_grade_page`/`_code_grade_render` context; `code_grade.html` currently renders `job.state`/`job.kind` for the grade job only.

### M5. The shutdown order rests on a draining mechanism that `shutdown_jobs()` does not trigger — §8 line 779 (via §6.11; `core.py`, `code_grade_runner.py`)
**What is wrong:** Section 6.11 says "stopping the grade runner first (draining) and then the install runner (terminating pip) avoids terminating pip while a grade still holds torch files, so grade shutdown precedes install shutdown." But in the listed code, `CodeGradeRunner.shutdown()` only joins the live thread (with a default 30 s timeout); it does not cancel anything, and `DashboardCore.shutdown_jobs()` never calls `cancel()`. "Draining" is a state entered via `cancel()` in `code_grade_runner.py`, not via shutdown. So the plan's rationale assumes a shutdown-triggered drain that does not exist, and section 8 lists no change to make shutdown cancel-or-drain grades, no install-runner shutdown timeout or join semantics, and no insertion position for the install runner relative to the scheduler, browser, and reverse runners in the existing `shutdown_jobs()` order (scheduler → browser → reverse → grade). The implementer must redesign shutdown to match the stated order, or the stated order is unimplementable.
**Evidence:** `core.py` `shutdown_jobs` (scheduler, browser, reverse, grade; no cancel call); `code_grade_runner.py` `shutdown` (join only) vs `cancel` (sets `cancelled`/draining); `browser_install.py` `shutdown` (stop + join) as the contrasting pattern; §8 line 779 ("in the order stated in section 6.11").

### M6. The B1 shared-scaffold refactor is incompletely planned, and the B3 condition is wrong — §8 lines 800, 815 (via §9 B)
**What is wrong:** Under B1, the scaffold is to be extracted from the browser and grade runners and used by "all three runners." Section 8's `browser_install.py` bullet (line 815) says "modify only if option set B picks the shared scaffold" — but that bullet describes extracting the scaffold without listing the corresponding changes: no bullet modifies `code_grade_runner.py` to adopt the scaffold (its bullet is message/ledger only), no bullet updates the browser runner's call sites or tests, and no scaffold filename or module is named. Under B3 ("generalize `BrowserInstallRunner`"), `browser_install.py` is also modified, yet line 815's condition ("only if B picks the shared scaffold") does not cover B3 — an implementer following section 8 literally would miss the B3 change entirely. Either way, the refactor's blast radius is understated in the file list.
**Evidence:** §8 lines 800, 815; §9 B1–B3; `browser_install.py` and `code_grade_runner.py` have visibly different state vocabularies and shutdown semantics (see M5), which is exactly the divergence B1 must reconcile but section 8 never maps.

### M9. TMPDIR and `$HF_HOME` handling stops at install/verify and never reaches the grade that needs it — §8 lines 771, 800 (via §5.3, §5.4)
**What is wrong:** Section 5.3 requires install and verification subprocesses to run with TMPDIR on a real disk, and section 5.4 requires `$HF_HOME` to point at a writable directory for service accounts. The implementer must design the env-propagation story.
**Evidence:** §8 lines 771, 800 (grade-runner bullet is message/ledger only); `docs/code-orchestrator.md` TMPDIR note (grade-time failure); §5.3/§5.4 (install/verify scope only).

### M10. Log retention contradicts itself — §8 line 771 (via §6.5, §6.10)
**What is wrong:** Section 6.5 says "The full log is retained beyond the 30-line tail," and section 6.10 says "The full log is retained (capped the same way the browser precedent caps its log, 256 KB, when the job finishes)." The implementer must decide what "full" means, where the retained copy lives, and how many retained logs are kept — and the section 10 "closing the tab loses nothing" criterion cannot be asserted against an undefined retention rule.
**Evidence:** §6.5/§6.10 wording; `browser_install.py` `_LOG_TAIL_LINES = 30`, `_MAX_LOG_BYTES = 262_144`, `_cap_log` (last-bytes truncation); §8 line 771 (no log-file plan).

### M12. Two further implementer decisions are delegated in prose that section 8 depends on — §8 lines 771, 779 (via §6.4, §6.1)
**What is wrong:** (a) Section 6.4: "the install may be queued or refused — queuing is the friendlier choice, but the implementer must pick one and the UI must show which." Queuing vs refusal changes the route behaviour, the job record, and the UI; it is a design decision, not an implementation detail, and section 8 contains no queue data structure, queued-state, or queue test. (b) Section 6.1: preflight "runs synchronously when the user starts an install, before any package is downloaded" — but the install itself is a background-thread job (§8 runner bullet). Section 8 never says whether synchronous preflight runs in the request handler (blocking the response, with what timeout and what response on refusal — a rendered list? a redirect with flashes?) or as the runner's first phase (in which case it is not synchronous from the user's perspective). The implementer must design the preflight request/response flow.

### N4. Section 8's test and doc bullets are not conditioned on the options they depend on — §8 lines 820, 843
